# Decisions: 업무 화면 공통 여백과 페이지 구조

- Date: 2026-11-02
- Status: Confirmed
- Feature: workspace-spacing-system
- Workflow: grill-me 인터뷰 완료. 이 문서는 결정만 기록하며 구현·Task 청사진은 memory-plan 이후 진행한다.
- 기준 코드: `d07b9a2`.
- 참조: 이 대화에 첨부된 DADAM 회의록 로그 화면 스크린샷. 화면 가장자리 약 10~12px, 검색 영역과 표 사이 약 10px라는 판단은 이미지 관찰에 따른 근사치이며 원본 CSS 측정값이 아니다.
- 출처 구분: **사용자 선택**은 네 차례의 1번 답변과 계획 단계의 D09 추가 답변, **코드 확인**은 저장소에서 확인한 사실, **설계 기본값**은 선택한 결과를 구현하기 위한 판단이다. 세부 구현값 전체를 사용자가 직접 지정한 것으로 취급하지 않는다.

## D01. 공통화 범위

- **Chosen**: 일반 업무 화면의 바깥 상하좌우 여백, 영역 사이 간격, 카드 내부 여백을 함께 공통화한다. 제작 캔버스와 팝업은 구조에 맞는 별도 공통 규칙으로 관리한다.
- **Source**: 사용자 선택 1번 — ‘바깥 여백 + 영역 사이 간격 + 카드 내부 여백까지 통일’.
- **Rationale**: 외곽만 줄이면 내부 카드·필터·입력 폼에 남은 중복 여백과 화면 간 차이를 해결하지 못한다.
- 대상은 `/workspace/*`의 목록·대시보드·설정·입력 화면과 로그인 후 홈(`/`)·관리자 진입 화면(`/admin`)이다. 홈과 관리자 진입 화면은 계획 단계 D09에서 사용자가 추가했다. Skill 등록/수정/조회, Template 목록과 적용 테스트도 포함한다.
- 아직 제목·설명만 있는 메뉴에는 동일한 공통 페이지 틀을 적용한다. 해당 메뉴의 업무 기능을 새로 개발하는 결정은 아니다.
- 로그인·인증 팝업·공개 랜딩 화면은 업무 화면 여백 변경의 대상이 아니다.

## D02. 상단 제목과 안내

- **Chosen**: 작은 화면 제목과 주요 버튼을 한 줄로 압축한다. 긴 설명은 필요할 때 펼쳐 보는 안내로 제공하고, mock 데이터 안내는 짧게 유지한다.
- **Source**: 사용자 선택 1번 — ‘작은 제목과 주요 버튼을 한 줄로 압축’.
- **Rationale**: 현재 제목·설명·예시 데이터 안내가 여러 줄로 쌓여 본문 시작 위치가 내려간다. 제목과 작업 진입점을 유지하면서 세로 공간을 줄인다.
- 페이지 제목은 의미상 `h1` 하나로 유지한다. 상세 제목·버전·저장/취소 등 기존 기능을 잃지 않도록 공통 헤더의 슬롯으로 수용한다.
- 안내 펼침은 키보드로 조작할 수 있어야 한다. 오류·검증 메시지·권한 안내·저장 중 상태를 설명 영역에 숨기지 않는다.
- 임시 저장 안내에는 mock 여부와 새로고침 시 초기화된다는 의미를 보존한다.
- 좁은 폭에서 버튼이 겹치면 줄바꿈한다. 텍스트나 조작 영역을 과도하게 축소해 억지로 한 줄에 넣지 않는다.

## D03. 업무 화면 푸터

- **Chosen**: 업무 본문의 공통 푸터인 앱 이름 / ‘나만의 업무 공간’을 제거한다. 내용 또는 페이지 이동 버튼 이후에는 공통 바깥 여백만 둔다.
- **Source**: 사용자 선택 1번 — ‘제거’.
- **Rationale**: 첨부 화면에 없는 반복 안내가 별도 높이를 차지하고 실제 작업 공간을 줄인다.
- 제거 대상은 `AppShell`의 본문 하단 푸터다. `NavSidebar` 하단의 사용자 프로필·권한 전환 영역, 모달의 저장/취소 버튼 영역은 별개의 기능이므로 유지한다.
- 데이터가 적을 때 화면 아래에 남는 자연스러운 빈 공간을 고정 행 높이·가짜 항목·불필요한 콘텐츠 늘리기로 채우지 않는다.

## D04. 모바일 상단 구조

- **Chosen**: 모바일 메뉴 버튼, 제목, 주요 버튼을 같은 상단 영역에 배치한다. 별도의 상단 빈 공간을 제거하고 바깥 여백은 PC와 같은 약 12px 기준으로 관리한다. 주요 버튼은 필요하면 다음 줄로 배치한다.
- **Source**: 사용자 선택 1번 — ‘메뉴 버튼 + 제목 + 주요 버튼을 같은 상단 영역에 배치’.
- **Rationale**: 현재의 독립된 고정 메뉴 버튼 때문에 일반 본문에 상단 64px 공간이 필요하다. 제목 줄과 통합하면 조작 버튼을 유지하면서 이 빈 공간을 줄일 수 있다.
- 기존 모바일 경계인 760px 이하 / 데스크톱 761px 이상과 사이드바 펼침 200px·접힘 64px 구조는 재사용한다.
- 메뉴 열기/닫기, Escape, 포커스 복귀, 본문 `inert`, 배경 스크롤 잠금, 역할별 메뉴 노출을 보존한다.
- 고정 헤더가 필요한 Skill 입력 화면 등은 공통 헤더 구조를 사용한다. 기존 `top-16` 같은 독립 오프셋은 실제 공통 헤더 구조와 맞추고 버튼 줄바꿈으로 본문이 가려지지 않게 한다.
- 이 결정은 이전 `2026-10-30-dadam-sidebar-layout-typography.md`와 `2026-10-30-dadam-look-and-feel.md`의 모바일 헤더 변경 제외를 이번 업무 화면 헤더 범위에서 대체한다. 기존 사이드바 기능·색상·프로필 구조까지 재설계하는 결정은 아니다.

## D05. 여백과 폭의 설계 기본값

- **Chosen**: 스크린샷의 밀도와 기존 dadam 간격값을 바탕으로 기본 간격을 12px로 정규화한다. 같은 역할의 간격은 같은 값을 참조한다.
- **Source**: D01·D04 및 코드 기반 설계 기본값. 바깥 약 12px는 D04에서 사용자가 선택했고, 나머지 역할별 기본값은 구현 판단이다.
- **Rationale**: `dadamUi.cardPadding`과 `sectionGap`이 이미 12px이다. 화면마다 10/12/16/20/28/38/40px을 따로 복제하는 구조를 줄인다.

| 역할 | 기본 기준 |
| --- | --- |
| 일반 페이지 바깥 상·하·좌·우 | 각각 12px |
| 주요 영역 사이·카드 사이 | 12px |
| 필터·폼·일반 카드의 내부 여백 | 12px |
| 버튼 묶음·필드 내부의 작은 간격 | 역할별 공통 4px/8px 기준 |
| 표 본문을 감싼 전용 표면 | 외부 패딩을 중복하지 않고 셀 여백에 맡김 |
| 제작 캔버스 | 캔버스 표면은 전체 사용, 도구/안내 영역은 별도 공통 규칙 |
| 모달·팝오버 | 페이지 외곽값과 분리한 공통 오버레이 규칙 |

- 기본 업무 페이지는 사이드바를 제외한 가용 폭을 사용한다. 현재 `AppShell.content.maxWidth: 1320px`와 자동 중앙 정렬로 생기는 추가 좌우 공백을 일반 페이지에서 제거한다.
- 외곽 패딩의 소유자는 `AppShell`의 본문 영역 한 곳으로 정한다. 자식 페이지 틀은 다시 같은 외곽 패딩을 더하지 않는다.
- 영역 간 간격, 카드 내부 여백, 표 셀 여백은 서로 다른 역할이다. 모든 margin/padding을 일괄적으로 12px로 치환하지 않는다.
- 표가 들어간 카드에서 카드 패딩과 셀 패딩이 겹치지 않게 내부를 구분한다. 제목/필터 부분은 내부 여백을 사용하고 표 부분은 필요한 경우 테두리까지 펼치는 공통 구성을 사용한다.
- 콘텐츠 읽기 폭·미리보기 비율·모달 최대 너비 등 의미 있는 제한은 해당 컴포넌트의 명시적 규칙으로 관리한다.

## D06. 하나의 설정 원본과 기존 컴포넌트 재사용

- **Chosen**: 여백 수치는 공통 CSS 변수에 모으고, 페이지 틀·헤더·카드가 해당 값을 사용하도록 구성한다. 기존 관리자 컴포넌트는 공통 구현을 감싸는 어댑터로 재사용한다.
- **Source**: 사용자 요구 ‘한 번에 관리’와 코드 기반 설계.
- **Rationale**: 현재 Tailwind 유틸리티와 Fluent UI/Griffel 스타일이 함께 사용된다. CSS 변수는 양쪽에서 같은 값을 참조할 수 있어 숫자 설정의 이중화를 피할 수 있다.
- 공통 수치의 원본은 `app/layout-tokens.css`로 모으고 `app/globals.css`에서 한 번 불러오는 구조를 기준으로 계획한다. `dadamUi`의 동일 역할 간격은 공통 변수 참조로 연결한다.
- 공통 페이지 틀과 헤더는 `components/layout` 아래에 두고, `AdminPage`는 기존 `title`, `description`, `dataNotice`, `actions` 계약을 보존하면서 공통 틀에 위임한다.
- `AdminCard`·`AdminMetric`·필터/툴바·`AdminPager`·Skill 입력 영역에서 레이아웃 역할에 해당하는 직접 지정값을 공통 기준으로 연결한다. 같은 카드/헤더를 별도 파일에 다시 구현하지 않는다.
- 새 일반 레이아웃에서 Tailwind 클래스를 사용하면 `app/admin-utilities.css`의 `@source`에 새 경로가 포함돼야 한다. 현재는 관리자 컴포넌트·관리자 훅·app만 명시적으로 탐색한다.
- 색상·폰트·그림자 체계를 전역 교체하거나 인증·Query·프로필·코멘트 Provider를 중복 생성하는 작업은 포함하지 않는다.
- 여백을 조절하는 운영자용 설정 화면이나 DB 저장 기능을 새로 추가하지 않는다. 개발자가 공통 설정 파일 한 곳에서 조정하는 구조다.

## D07. 특수 화면과 기능 보존

- **Chosen**: 제작 캔버스·모달은 같은 설정 체계 안에서 별도 역할을 사용하고, 기존 상태와 업무 기능을 보존한다.
- **Source**: 사용자 선택 D01 및 코드 기반 제약.
- **Rationale**: 캔버스 좌표와 팝업 최대 크기는 일반 게시판 패딩과 다른 의미를 가진다.
- 제작 화면은 `CommentsWorkspace`의 표면 좌표·핀 이동·팝업 경계 계산을 기준으로 한다. 헤더 위치 변경을 저장된 좌표의 일괄 재작성으로 해결하지 않는다. 모바일 메뉴와 도구가 핀 조작을 가리지 않도록 한다.
- 일반 모달은 `ModalFrame`의 헤더/본문/버튼 영역을 재사용한다. 외곽 안전 간격·내부 스크롤·포커스 복귀를 공통 오버레이 값으로 관리하며 코멘트 팝업의 좌표/크기 정책과 혼동하지 않는다.
- 검색·필터·정렬·페이지 이동·탭·공개 범위·CRUD 권한·폼 검증·미저장 확인·내용 버전·재적용·다운로드를 보존한다.
- 로딩·빈 상태·오류·조회 전용에서도 동일한 페이지 바깥 기준을 적용한다. 접근 권한이 없는 버튼은 기존처럼 렌더링하지 않는다.
- 백엔드 API·mock 저장소·Cosmos DB 모델·인증 계약·서버 액션의 변경은 필요하지 않다. 새 라이브러리를 추가할 사유도 현재 확인되지 않았다.

## D08. 확인한 기존 구조와 검증 방침

- **Chosen**: 계획에서 기존 구조를 활용하고 자동 검증과 실제로 미실시한 검증을 구분한다.
- **Source**: 코드 확인 및 기존 검증 정책.
- **Rationale**: 이번 변경은 공통 부모와 화면별 레이아웃을 동시에 정리해야 하며, 과거 화면 위치를 가정한 검사가 새 사용자 결정을 방해해서는 안 된다.

| 확인 위치 | 현재 상태와 계획 시 고려점 |
| --- | --- |
| `components/layout/AppShell.tsx` | 일반 40px/38px, 일부 관리자 22px/28px, 모바일 상단 64px, 제작 0px로 분기. 본문 푸터도 별도 높이 사용 |
| `components/admin/ui/AdminPrimitives.tsx` | 공통 페이지 gap 16px, 카드 padding 16px. 기존 컴포넌트를 재사용할 수 있음 |
| `components/admin/skills/SkillEditorPage.tsx`, `SkillRuleFields.tsx` | 자체 헤더와 gap 20px, 내부 padding 16px. 최근 구현한 등록 화면도 공통 기준으로 이관 필요 |
| `lib/ui/dadam-theme.ts` | 카드/영역 간격 12px이 있으나 관리자 일반 페이지에는 일관되게 연결되지 않음 |
| `components/ui/ModalFrame.tsx` | 이미 공통 모달 존재. 같은 역할의 새 모달을 중복 생성하지 않음 |
| `tests/e2e/admin-comments-merge.spec.ts` | 모바일 제목이 메뉴 버튼 아래에 있어야 한다는 과거 배치 assertion 존재. D04에 맞춰 보존할 동작과 변경할 배치 기대를 구분해야 함 |

- 계획/실행 시 의미 있는 단위·jsdom 통합 검사, `npm.cmd run typecheck`, `npm.cmd run lint`, `npm.cmd run build`, 정적 코드 검토를 기준으로 한다. 간격 숫자를 그대로 복사한 테스트를 대량 생성하지 않는다.
- 기존 지속 정책 `.memory/decisions/2026-10-30-task-validation-policy.md`의 ‘수동 브라우저 검증, Computer Use, 브라우저 E2E, 스크린샷/육안 비교 … 제외’를 따른다. 현재 사용자가 제공한 스크린샷을 설계 참고로 읽는 것과 새 브라우저 검증을 수행하는 것은 구분한다.
- 이전 Skill 작업 보고서에는 브라우저 검사 실행 이력이 있지만, 그 이력을 향후 전체 Task에 대한 기존 제외 정책의 자동 폐지로 해석하지 않는다. 이 결정에서는 새 브라우저 검증을 완료 조건에 추가하지 않는다.
- 기존 E2E의 배치 기대를 새 구조에 맞게 정리할 필요는 계획에 명시하되, 실행하지 않은 브라우저 검사를 통과했다고 기록하지 않는다.
- 이 인터뷰에서는 앱 코드를 변경하거나 테스트·빌드·브라우저 검증을 실행하지 않았다.

## D09. 홈과 관리자 진입 화면 포함 — 계획 단계 추가 결정

- `app/(authenticated)/page.tsx`와 `app/(authenticated)/admin/page.tsx`의 자체 큰 헤더/카드 여백을 공통 페이지·카드 규칙으로 이관한다. 홈의 장식 그림 크기는 페이지 간격과 구분한다.
- `/admin`의 서버 `requireRole(APP_ROLES.ADMIN, "/admin")`를 유지한다. 홈·관리자 화면에 새 업무 기능이나 mock 데이터를 추가하지 않는다.
- 이에 따라 `AppShell`의 별도 고정 모바일 메뉴 버튼과 본문 푸터는 인증된 업무 셸 전체에서 제거할 수 있다. 사이드바 프로필과 팝업 버튼 푸터는 유지한다.
