## D02. 관리자 화면과 메뉴 통합

- **Chosen**: 활동 로그, 대시보드, 사용자 설정을 각각 유지하고 모델 설정과 토큰·비용 관리를 하나로 통합한다. 이번 구현 대상은 이 4개 화면이다.
- **Rationale**: 사용자가 확정도가 높은 관리자 기능을 우선 구현하고 마지막 두 메뉴를 합치도록 요청했다.
- 통합 메뉴의 작업명은 `모델·토큰 관리`이며, 내부에 `모델 설정`과 `토큰·비용` 탭을 둔다.
- 현재 사이드바의 `운영 정책` 항목이 HTML의 모델 설정에 대응한다. 별도 운영 정책 화면을 추가로 중복 구현하지 않는다.
- 프롬프트 세트·Skill·Template의 본문 기능이나 일반 업무 화면의 구현은 포함하지 않는다. 기존 메뉴와 안내 화면은 유지한다.
- 기존 policy/tokens 경로와 프로필의 토큰 관리 진입 링크는 통합 화면의 해당 탭으로 이어지도록 계획한다.

## D03. 화면 간 연결이 동작하는 mock

- **Chosen**: 조회뿐 아니라 수정·승인·반려가 동작하고 다른 화면에도 반영되는 mock으로 구현한다. 사용자 선택: 첫 질문 1번.
- **Rationale**: 디자인 검토와 함께 실제 업무 흐름을 검증하고, 이후 데이터 연결 시 화면 로직을 재사용한다.
- 사용자 변경 → 활동 로그 기록 → 대시보드 집계 반영을 연결한다.
- 기존 프로필의 토큰 추가 신청 → 관리자 승인 대기 목록 → 승인/반려 → 신청 상태·개인 한도 표시를 연결한다.
- 신청 제출만으로 한도를 올리지 않으며, 승인 시 한 번만 반영한다. 이미 처리한 요청의 중복 승인은 막는다.
- 화면마다 별도 사용자·신청·사용량 배열을 만들어 서로 다른 결과를 보여주지 않는다.
- mock 작업이 실제 계정·메일·모델 호출·청구를 처리한 것처럼 표현하지 않는다.

## D04. 역할 명칭

- **Chosen**: 슈퍼 관리자(전사 관리자), 관리자(부서 관리자), 일반 사용자의 3단계 명칭을 적용한다. 사용자가 직접 정정한 용어를 따른다.
- **Rationale**: 기존 앱의 기술적 역할 이름과 업무 기획의 역할 명칭을 구분하고, 관리자 두 종류의 범위를 명확히 한다.

| 업무 명칭 | 의미 | 첨부 HTML의 대응 명칭 |
| --- | --- | --- |
| 슈퍼 관리자 | 전사 관리자 | 관리자 / 전사 관리자 |
| 관리자 | 부서 관리자 | 부서 관리자 |
| 일반 사용자 | 일반 업무 사용자 | 일반 사용자 |

- 현재 실제 인증의 `Admin`·`User`는 아직 2단계다. 업무 역할 3단계가 이미 실제 인증에 구현되어 있다고 간주하지 않는다.

## D05. 제작 아래 구분선을 기준으로 한 메뉴 노출

- **Chosen**: `제작` 메뉴 아래 구분선 위의 메뉴는 일반 사용자·관리자·슈퍼 관리자에게 표시한다. 구분선 아래의 메뉴는 관리자·슈퍼 관리자에게 표시하며 일반 사용자에게는 렌더링하지 않는다. 사용자의 마지막 설명을 적용한다.
- **Rationale**: 메뉴 그룹에 접근할 수 있는 최소 역할과, 접근한 화면에서 가능한 작업을 별개로 다룬다.
- 위쪽: RFP 등록, 검토 목록, AI 분석, 파일 업로드, 목차, 제작 설정, 제작.
- 아래쪽: 프롬프트 세트, Skill, Template, 통합 모델·토큰 관리, 사용자 설정, 대시보드, 활동 로그.
- 아래쪽 메뉴를 부서 관리자에게 보여준다고 해서 전사 데이터 조회나 슈퍼 관리자 전용 설정 변경까지 허용하지 않는다.
- 통합 메뉴에서 부서 관리자가 사용하는 영역은 소속 부서 토큰 조회·신청 처리다. 전사 모델·단가·환율 설정 액션은 슈퍼 관리자에게만 제공한다.
- 프롬프트 세트·Skill·Template도 이번에 정한 메뉴 그룹 노출 기준을 따르지만, 본문 CRUD 기능을 새로 구현하거나 권한 편집 대상에 추가하지 않는다.
- 메뉴·액션 권한은 조건부 렌더링으로 적용한다. CSS 숨김을 권한 검사로 대신하지 않는다.

## D06. 역할별 CRUD 권한표와 적용 범위

- **Chosen**: 사용자별 개별 권한 대신 역할별로 생성(Create)·조회(Read)·수정(Update)·삭제(Delete)를 설정한다. 적용 대상은 이번 관리자 기능으로 한정한다. 사용자 선택: 역할별 CRUD 1번, 적용 범위 1번.
- **Rationale**: 같은 역할의 정책을 한곳에서 관리하고, 미확정인 일반 업무 기능까지 이번 작업을 확대하지 않는다.
- 대상: 사용자·그룹, 모델·비용 설정, 토큰 관리, 대시보드·활동 로그의 이번 구현 기능.
- 조회 전용 기능에는 의미 없는 생성·수정·삭제 체크박스를 제공하지 않는다. 제공 여부는 실제 업무 동작에 맞춘다.
- 역할별 권한 설정은 슈퍼 관리자가 담당한다.
- 권한표가 전사/부서 데이터 범위를 확대하거나, 일반 사용자에게 아래쪽 관리자 메뉴를 열어주는 수단이 되어서는 안 된다.
- 토큰 승인·반려는 별도의 업무 처리 규칙으로 검사한다. CRUD의 수정 권한이 있다고 다른 부서 신청이나 슈퍼 관리자 전용 설정을 변경할 수 있게 하지 않는다.
- 본인 권한을 임의로 올리거나 슈퍼 관리자 전용 경계를 무효화하는 조작은 허용하지 않는다.

## D07. 부서 관리자의 기본 범위

- **Chosen**: 부서 관리자는 소속 부서 사용자·사용량 조회와 토큰 신청 승인·반려를 담당한다. 사용자 추가·수정·삭제 및 역할·권한 설정은 슈퍼 관리자가 담당한다. 사용자 선택: 조회·토큰 승인만 1번.
- **Rationale**: HTML에 설명된 부서 관리자의 기본 역할을 유지하면서 사용자 관리 권한 확대를 피한다.
- 부서 관리자의 토큰 승인은 해당 부서 신청에 한정한다. 승인에 따른 한도 반영과 임의의 전사·개인 한도 설정 변경은 구분한다.
- 소속 부서가 확인되지 않는 경우 전사 범위로 대체하지 않는다.

## D08. 대시보드·로그의 데이터 범위

- **Chosen**: 부서 관리자에게도 대시보드·활동 로그를 제공하되 소속 부서 데이터만 조회하도록 한다. 슈퍼 관리자는 전사 데이터를 조회한다. 사용자 선택: 부서 범위 조회 1번.
- **Rationale**: 부서 운영에 필요한 가시성을 제공하면서 다른 부서의 정보는 노출하지 않는다.
- 목록뿐 아니라 검색 후보, 상세, 차트, 합계, 사용자 수, 필터 결과, 내보내기에도 동일한 범위를 적용한다.
- 먼저 허용된 데이터 범위를 정한 뒤 검색·기간 필터·집계·페이지 처리를 수행한다.
- 활동 로그는 HTML의 기간·사용자·대상·액션·리소스·성공/실패 필터, 정렬, 상세 펼침, CSV 내보내기 흐름을 참고한다.

## D09. 대시보드 4개 탭

- **Chosen**: RFP 현황 / 사용량 트렌드 / 작업·리소스 상세 / 사용자별 현황의 4개 탭을 구현하고 기간 필터를 공통 적용한다. 사용자 선택: 4개 탭 구현 2번.
- **Rationale**: 실제 HTML 코드의 RFP 고정 상태보다 가이드에 설명된 분석 범위까지 구현하기로 사용자가 선택했다.
- RFP 현황: 요약 지표, 등록 추이, 결과 분포, 부서별 현황, RFP 목록.
- 사용량 트렌드: 활동 이벤트·토큰 사용·활성 사용자 추이와 막대/선 전환.
- 작업·리소스 상세: 액션·리소스·세부 작업별 집계.
- 사용자별 현황: 허용 범위의 사용자별 활동·사용량 집계.
- 같은 기간·범위의 로그와 사용량을 공통 데이터에서 집계한다. 서로 다른 고정 숫자를 화면에 직접 박아 넣지 않는다.

## D10. 모델별 비용 상세와 단가 설정

- **Chosen**: 토큰 한도 관리뿐 아니라 모델별 입력·출력 토큰, 각각의 단가, 모델별 예상 비용 집계와 단가 설정 화면을 포함한다. 사용자 선택: 비용 상세 2번.
- **Rationale**: 단일 예시 단가로 총 토큰만 환산하는 HTML보다 모델별 비용을 구분하여 검토할 수 있어야 한다.
- 업무별 기본 모델 선택은 HTML의 구성을 참고한다.
- 비용·모델 설정은 전사 정책이므로 슈퍼 관리자 관리 영역으로 둔다. 부서 관리자는 허용된 소속 부서의 사용·비용 내역만 조회한다.
- 초기 단가·사용 내역은 예시 데이터다. 실제 공급자의 최신 요금이나 실제 청구 금액이라고 표시하지 않는다.
- 모델 연결용 비밀 키·실제 엔드포인트 등록·외부 모델 호출은 이번 범위에 포함하지 않는다.

## D11. 통화와 비용 이력

- **Chosen**: 입력·출력 각각 100만 토큰당 USD 단가를 등록하고, 관리자가 설정한 USD/KRW 환율로 원화 예상 비용을 표시한다. 사용 당시 단가·환율을 사용 내역에 보관한다. 사용자 선택: 통화 1번, 과거 비용 처리 1번.
- **Rationale**: 단가 기준을 통일하고, 설정 변경으로 과거 집계 값이 달라지지 않게 한다.
- 비용 기준: `(입력 토큰 × 입력 USD 단가 + 출력 토큰 × 출력 USD 단가) / 1,000,000`에 당시 환율을 적용한다.
- 단가·환율 변경은 이후 사용 내역부터 적용한다. 기존 내역을 최신 설정으로 소급 재계산하지 않는다.
- 금액의 보관 정밀도·합산·표시 반올림 기준은 계획에서 일관되게 명시한다. 토큰 수와 금액 단위를 혼용하지 않는다.
- 자동 환율 조회·실제 청구서 연동은 포함하지 않는다.

## D12. 디자인 변경을 고려한 컴포넌트 구성

- **Chosen**: 레이아웃·배치·간격은 Tailwind를 사용하고 기존 Fluent UI의 버튼·입력·모달을 재사용한다. 사용자 선택: Tailwind + Fluent UI 1번.
- **Rationale**: 프로젝트의 Tailwind 우선 규칙을 따르면서 기존 접근성 동작과 컴포넌트를 활용한다.
- 색상·글꼴·간격·모서리 등의 디자인 값을 공통 설정으로 모으고 Fluent 테마와 새 레이아웃에서 일관되게 사용한다.
- 기본 UI와 반복되는 지표 카드·필터·표·페이지 이동·상태 표시를 공용화한다. 업무 전용 폼과 승인 규칙은 공용 UI에 섞지 않는다.
- `components/ui/ModalFrame.tsx`, `SegmentedControl.tsx`, `ToggleSwitch.tsx`, `components/providers/FluentUiProvider.tsx`와 기존 프로필·토큰 모달을 우선 검토한다.
- 기존 사이드바·프로필·로그인 전체를 Tailwind로 변환하지 않는다. 새 스타일의 전역 초기화가 기존 Fluent 화면을 깨뜨리지 않도록 확인한다.
- 최종 디자인에서 색상 등은 공통 설정 중심으로 교체하되, 정보 구조나 배치가 달라질 때는 화면 구성 수정이 필요할 수 있다.

## D13. 코드 확인으로 정한 데이터 처리 기본값

- **Chosen**: 화면 → TanStack Query → 타입이 있는 데이터 서비스 → mock 저장소로 분리한다. 기존 프로필과 동일하게 브라우저 메모리에서 변경을 유지하고 전체 새로고침하면 초기화한다.
- **Rationale**: 프로젝트의 데이터 조회 규칙을 지키고 기존 mock의 수명과 일치시키면서 데이터 공급원을 이후 교체할 수 있도록 한다. 사용자의 별도 새 저장 요구는 없으므로 로컬 영구 저장소를 추가하지 않는다.
- mock 저장소와 Query 캐시를 구분한다. 화면 이동이나 캐시 갱신으로 저장한 mock 작업이 사라지지 않게 한다.
- 기존 프로필 토큰 데이터·신청 목록을 통합해 동일한 요청을 중복 저장하거나 한도를 각각 계산하지 않는다.
- 기존 사용량 예시의 기준 기간과 합계 72.4K를 고려하여 입력·출력·모델별 내역을 정합성 있게 준비한다. 고정 기간과 새 작업의 생성 시각을 섞어 현재 변경이 필터에서 사라지지 않게 한다.
- Zod로 입력·데이터 경계를 검증하고, 전체 타입에서 Pick/Omit 등으로 하위 타입을 정의한다. 내부 코드에 any/unknown을 새로 도입하지 않는다.
- 사용자·부서·모델·신청·로그 간 참조는 안정적인 ID로 연결한다. 표시 이름을 권한 판단의 키로 사용하지 않는다.
- 로딩·빈 결과·검증 실패·처리 실패·중복 처리 상태를 공용 UI와 업무 규칙에서 구분한다.
- Cosmos DB 연결은 후속 범위다. 이번에는 컨테이너·파티션 키·인덱스·프로비저닝을 확정하거나 리소스를 생성하지 않는다.

## D14. 현재 인증 경계와 후속 실제 연동

- **Chosen**: 이번 데이터·업무 동작은 mock이다. 3단계 역할 시연과 실제 로그인 권한을 분리하며 기존 서버 인증·인가를 보존한다.
- **Rationale**: 클라이언트에서 바꿀 수 있는 역할·체크박스는 실제 권한의 신뢰 근거가 될 수 없다.
- `AUTH_ENABLED=false`의 기존 개발 미리보기를 3단계 업무 역할 검토에 활용한다. 이 상태로 실제 관리자 API·DB·메일을 호출하지 않는다.
- 인증 활성 상태에서는 기존 서버의 세션·Admin 검사와 미리보기 역할 변경 금지를 유지한다. 클라이언트 role이나 부서 선택값으로 서버 접근 권한을 늘리지 않는다.
- 실제 Entra 역할을 3단계로 변경하거나 부서 정보를 인증에 추가하는 작업은 이번에 임의로 포함하지 않는다. 후속 실제 연동에서는 신뢰 가능한 사용자·부서·권한 데이터를 서버에서 확인해야 한다.
- 이후 서버 API/Server Action을 연결할 때 입력 검증·행위 권한·대상 부서 범위를 서버에서 다시 검사한다. 화면에서 계산한 비용·승인 후 한도를 그대로 저장하지 않고 서버가 검증·계산한다.

## D15. 계획·실행 단계의 검증 기준

- **Chosen**: 다음 memory-plan에서 파일·심볼·스키마·검증 명령·Task를 구체화한다. 이번에는 결정 문서만 저장한다.
- **Rationale**: 사용자와 확정한 제품 동작을 유지하면서 구현 세부사항은 코드와 함께 검증 가능한 청사진으로 만든다.
- 우선 검증: 세 역할의 메뉴 노출, 부서 범위의 목록·집계·내보내기, 역할별 CRUD 및 슈퍼 관리자 전용 액션.
- 업무 검증: 신청의 승인/반려 전이, 중복 승인 방지, 한도·프로필 동기화, 로그·대시보드 집계 일치.
- 비용 검증: 모델별 입력/출력 단가 계산, 환율 환산, 변경 후 과거 비용 보존, 합산과 반올림의 일관성.
- UI 검증: 4개 화면과 대시보드 탭, 필터·정렬·페이지 이동·모달, 좁은 화면, 키보드, 로딩·오류·빈 상태, 기존 프로필·사이드바 회귀.
- 코드 변경 단계에서 `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`와 필요한 브라우저 검증을 계획한다. 이번 문서 저장을 구현 테스트 통과로 표현하지 않는다.

## 관찰 사항과 범위 밖 후속 보고

- `config/sidebar.ts`에 이미 일반 7개와 관리자 8개 메뉴가 정의되어 있고 본문은 대부분 안내 화면이다. 메뉴 통합 및 3단계 노출은 이 기존 카탈로그를 수정하는 방향이며 새 사이드바를 중복 구현하지 않는다.
- `config/token-preview.ts`의 신청 상태는 현재 pending 하나뿐이고, 기존 프로필 한도는 고정값이다. 승인/반려와 공유 한도 상태로 확장해야 이번 연결 흐름이 동작한다.
- 기존 프로필의 `department`는 null일 수 있다. 실제 세션에는 부서 정보가 없어 서버의 부서 범위 검증은 별도 연동 과제다. 실제 조직·인사 시스템 연결을 이번 기능으로 임의 추가하지 않는다.
- HTML 사용자 목록의 체크박스는 대상 사용자 선택용이다. 이번 역할별 CRUD 편집은 사용자가 인터뷰에서 선택한 추가 설계다.
- HTML 대시보드의 `DB.tab = 'rfp'` 고정과 가이드의 4개 탭 설명은 서로 다르다. 이번에는 사용자 선택에 따라 4개 탭을 구현한다.
- `package.json`에 Fluent UI·Zod·Vitest는 있으나 Tailwind·TanStack Query는 없다. 필요한 의존성 추가는 다음 계획·실행 단계에서 처리한다. 별도 UI 라이브러리나 차트 라이브러리 도입은 이번 인터뷰로 확정하지 않는다.
- `package-lock.json`에는 작업 시작 전부터 사용자 변경이 있다. 이번 인터뷰에서는 수정하거나 되돌리지 않았다.
- IDE에 표시된 `.memory/decisions/2026-09-22-kpc-app-template-review.md`는 현재 경로에서 찾을 수 없었다. 없는 파일의 내용을 추정하여 근거로 사용하지 않았다.
