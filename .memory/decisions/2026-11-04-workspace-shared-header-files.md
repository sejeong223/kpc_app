## D01. 공통 연결과 파일 화면 개선을 함께 진행

- **Chosen — 사용자 선택 1**: 공통 프로젝트 상태·상단바 연결과 파일 업로드 개선을 이번 범위에 포함한다.
- **Rationale**: 파일 화면만 개선하면 메뉴 이동 시 프로젝트·회차가 달라지는 문제가 남는다. 공통 기준을 먼저 정리한 뒤 파일 UI를 개선한다.
- 범위는 비교 보고서의 R1~R5다. 프로젝트 선택/회차 불일치, 상단바 부분 대응, 로컬 저장 안내, 파일 추가 클릭 단계, 웹 기간·우선순위 표시를 다룬다.
- 실제 서버 저장·문서 분석·웹 검색·AI 연결은 기존대로 후속이다. 이번에도 mock 프로젝트와 실제 브라우저 로컬 저장을 사용한다.

## D02. 작업 메뉴 6개에 공통 기준 적용

- **Chosen — 사용자 선택 1**: AI 분석·파일 업로드·목차·제작 설정·제작·리뷰에 동일한 프로젝트 선택·회차·상단바 기준을 적용한다.
- **Rationale**: AI 분석·리뷰도 같은 상단바를 사용하며 사이드바 리뷰 노출이 헤더의 프로젝트 상태를 참조한다. 일부 메뉴만 연결하면 기준이 둘로 남는다.
- 대상 경로: `/workspace/analysis`, `/workspace/files`, `/workspace/toc`, `/workspace/setup`, `/workspace/write`, `/workspace/review`.
- AI 분석·리뷰는 공통 상단바와 프로젝트 접근 기준까지만 연결한다. 분석·리뷰 본문 기능을 새로 구현하지 않는다.
- 리뷰의 PM 조건을 선택 프로젝트에서 계산한다. 슈퍼 관리자의 전체 프로젝트 접근 원칙을 적용한다. 프로젝트 접근과 리뷰 접근을 구분하고, 권한 없는 액션/메뉴는 조건부 렌더링한다.
- 리뷰 접근이 불가능한 프로젝트로 전환하면 해당 선택을 유지한 제작 화면으로 이동한다. 잘못된 프로젝트 ID를 다른 프로젝트로 조용히 바꾸지 않고 오류/선택 경로를 제공한다.
- RFP 등록·검토 목록·완료한 제안·관리자 메뉴의 본문 개발은 포함하지 않는다.

## D03. 동료의 제작 화면과 핀 UI 유지

- **Chosen — 기존 명시적 요청 및 이번 인터뷰에서 제시한 유지 조건**: 제작의 동료 화면·핀 위치 방식·팝업·답글·멘션·키보드 조작을 유지하면서 데이터 연결을 변경한다.
- **Rationale**: 사용자는 새 제작 편집기 대신 동료 화면으로 복원하도록 요청했다. 공통 연결을 새 편집기로 다시 교체하는 작업으로 확대하지 않는다.
- `/workspace/write`는 현재 동료 제작 화면을 기준으로 한다. 이전에 만든 슬라이드 편집기를 기본 화면이나 별도 편집 탭으로 다시 노출하지 않는다.
- 새 핀의 좌표 기준은 동료 화면의 제작 작업 영역이다. 현재 슬라이드가 없는 화면에 임의의 소목차·슬라이드 ID를 붙이지 않는다.
- 공통 상단바는 동료 컴포넌트의 표현과 기존 Dadam 컨트롤을 재사용한다. 메뉴별 상단바·선택기를 중복 표시하지 않는다.

## D04. 통합 작업 상태를 공통 데이터 원본으로 사용

- **Chosen — 코드 기반 구현 기본값**: `WorkspaceProjectProvider`/`createWorkspaceRuntime`, 기존 프로젝트 선택·회차 저장소를 중심으로 연결한다. 헤더용 별도 `useState("mois")`를 업무 상태의 원본으로 유지하지 않는다.
- **Rationale**: 파일·목차·제작 설정은 이미 프로젝트별 IndexedDB와 선택 복원·충돌 검사를 사용한다. 헤더가 이를 구독해야 메뉴 이동과 새로고침 이후에도 상태가 일치한다.
- 프로젝트 ID, 사용자 저장 범위, 현재 회차, 작업/완성 상태, 권한, 의견 수, 회차 이력은 공통 업무 상태에서 계산한다.
- 사이드바·상단바·본문이 같은 공급자에 접근하도록 Provider 배치를 계획 단계에서 정리한다. 독립 인스턴스나 저장소를 중복 생성하지 않는다.
- 기존 URL 선택값과 저장된 선택값을 존중하고, 6개 메뉴에서 일관되게 처리한다. 프로젝트·사용자 전환 시 캐시·대기 응답·모달·미리보기·코멘트 편집 범위를 분리한다.
- 프로젝트 이름·번호·PM·참여자는 기존 카탈로그를 사용한다. 발주처·마감 등 카탈로그에 없는 표시 정보는 같은 프로젝트 ID의 mock 메타데이터로 보강할 수 있지만 없는 값을 다른 프로젝트에서 가져오지 않는다. 예산 등 겹치는 값의 원본을 하나로 정한다.
- 이전 헤더 mock의 고정 PM 역할·권한·회차·완성본 숫자를 실제 로컬 작업값 대신 사용하지 않는다. 프로젝트 선택이 인증 역할이나 관리자 메뉴 권한을 바꾸지 않는다.

## D05. 설정창은 권한 저장까지 연결

- **Chosen — 사용자 선택 1**: 권한 저장을 공통 작업 상태에 연결한다. 기본정보는 조회용으로 표시하고, 기본정보 수정·알림·프로젝트 활동 로그는 후속으로 둔다.
- **Rationale**: 권한 도메인은 이미 있지만 기본정보 수정·알림·로그의 업무 저장 모델은 별도로 필요하다. 이번 공통 연결에 필요한 범위를 우선한다.
- 권한 설정 자체는 기존 합의대로 PM·슈퍼 관리자만 변경한다. 참여자에게 목차 구조 변경, 담당 지정, 제작 설정, 완성, 재작업을 각각 위임한다.
- PM·슈퍼 관리자의 고정 전체 권한은 해제할 수 없다. 부서 관리자라는 이유만으로 프로젝트 관리 권한을 자동 부여하지 않는다.
- 헤더 mock의 `권한 부여` 재위임 체크박스를 실제 권한으로 새로 추가하지 않는다. UI 체크 항목을 기존 업무 권한 계약에 맞춘다.
- 체크 변경은 저장 전 초안이다. 저장 성공 후 공통 권한·액션 노출에 반영하고 실패하면 입력을 보존한다. 여러 사람을 함께 저장하는 UI는 일부만 저장된 상태를 성공으로 표시하지 않도록 검증·저장 단위를 계획한다.
- 이번에 연결하지 않는 알림·로그는 실제 저장/발송/활동 이력처럼 작동하거나 표시하지 않는다. 임시로 체크만 바뀌는 입력이나 다른 프로젝트의 시연 로그로 채우지 않는다. 기존 탭을 유지할 경우 미연결 상태를 명확히 처리한다.

## D06. 핀 코멘트를 프로젝트·회차별로 관리

- **Chosen — 사용자 선택 1**: 프로젝트와 회차에 따라 코멘트를 구분한다. 이전 회차는 이력으로 보존한다.
- **Rationale**: 기존 `production-preview` 저장 범위에는 프로젝트·회차가 없어 프로젝트를 변경해도 같은 코멘트를 표시한다.
- 신규 코멘트에는 사용자 저장 범위·프로젝트·회차·화면 좌표의 연결을 명시한다. 같은 회차 번호라도 다른 프로젝트 의견을 섞지 않는다.
- 새 코멘트 저장은 공통 프로젝트 저장·버전 검사 경계에 연결하여 회차 전환과 의견 보관이 함께 확정되게 한다. 헤더만 회차를 바꾸고 코멘트가 이전 회차에 남는 별도 저장 흐름을 만들지 않는다.
- 기존 프로젝트 데이터에 있는 슬라이드별 코멘트는 원래 소목차·슬라이드 연결을 보존한다. 화면 전체 핀으로 임의 변환하거나 삭제하지 않는다. 화면 전체 의견과 슬라이드 의견을 구분 가능한 모델로 확장하고, 집계 시 중복 계산하지 않는다.
- 화면 전체 의견은 임의 소목차의 미처리 의견 수에 더하지 않는다. 프로젝트 전체 집계에는 포함할 수 있다.
- 기존 코멘트의 `isSeed` 표시는 시연 여부로 보존한다. 프로젝트별 신규 저장에 과거 시연 댓글을 실사용자가 새로 작성한 것처럼 복제하지 않는다.

## D07. 화면 전체 코멘트 처리 상태 권한

- **Chosen — 사용자 선택 1**: 해당 코멘트의 작성자·PM·슈퍼 관리자가 `반영 완료`·`다시 열기`를 할 수 있다.
- **Rationale**: 화면 전체 핀에는 소목차 담당자가 없다. 작성자가 자신의 의견 처리 여부를 확인하고, 프로젝트 관리자가 전체를 관리하도록 한다.
- 프로젝트 접근 가능 여부와 현재 회차/읽기 전용 여부를 먼저 확인한다. 숨긴 버튼을 우회해 명령을 호출해도 같은 규칙을 업무 로직에서 검증한다.
- 이 선택은 상태 변경 권한에 대한 것이다. 본문·답글의 본인 수정/삭제, 대화 전체 삭제, 핀 이동 등은 동료 기능의 기존 동작을 보존하되 프로젝트 접근·회차 불변 규칙을 적용한다. 불필요하게 다른 사람의 본문 편집 권한을 확대하지 않는다.
- 기존 슬라이드별 코멘트에는 기존 소목차 담당자·PM·슈퍼 관리자 상태 처리 규칙을 유지한다. 화면 전체 의견의 새 규칙을 슬라이드 의견에 무조건 덮어쓰지 않는다.
- 프로젝트 참여자만 멘션 후보로 제공하고, 입력·저장 시에도 대상을 검증한다. 새 알림 발송 기능은 추가하지 않는다.

- **Source**: `2026-11-03-workspace-toc-production.md` D11. 이번 인터뷰에서 기존 합의를 재사용한다고 안내했다. 이번에 새로 선택받은 항목으로 표기하지 않는다.
- **Rationale**: 원본에는 프로젝트/회차 식별자가 없으므로 어느 프로젝트에 자동 배정해야 하는지 알 수 없다.
- `kpc-pin-comments` 원본 저장소, 의견·답글·작성자·시간·처리 상태·핀 좌표를 보존한다. 새 프로젝트나 첫 번째 프로젝트에 임의 이관하지 않는다.
- `useLegacyComments`와 `readExisting` 및 `LegacyCommentsArchive`를 재사용한다. 과거 데이터가 없는 사용자에게 보관함 시연 데이터를 새로 생성하지 않는다.
- 수동 프로젝트 배정/이관 기능과 원본 삭제는 이번 범위에 추가하지 않는다.

## D09. 완성·재작업·이력은 기존 업무 규칙 재사용

- **Chosen — 공통 상태 연결 범위와 기존 확정 정책에서 도출**: 상단바의 완성·재작업·회차 이력을 기존 통합 업무 로직에 연결한다. 파일 화면의 다음 회차와 별개의 회차를 만들지 않는다.
- **Rationale**: 목차에는 이미 완성·재작업이 구현되어 있다. 새 헤더용 업무 로직을 만들면 같은 기능의 동작이 달라진다.
- 미완료 소목차·의견·체크리스트를 확인한 뒤 현재 상태를 보관할 수 있으며 미완료 항목을 자동 완료로 바꾸지 않는다.
- 완성본은 읽기 전용이다. 완성 전 재작업은 `미완성 이력`으로 보관하고 완성본 수와 구분한다.
- 새 회차는 파일 자료·참조 순서를 계승하고 완료 섹션을 고정한다. 기존 정책대로 미처리 코멘트만 새 ID와 원본 연결을 가진 사본으로 이어가고, 처리된 의견은 과거 이력에 남긴다. 화면 전체 핀에도 같은 회차 보존 기준을 적용한다.
- 이력 조회는 당시 파일·설정·의견을 읽기 전용으로 보여준다. 동료 제작 화면의 핀 표현을 유지하며 이력 진입 때문에 다른 편집기로 화면을 교체하지 않는다.
- PPT는 실제 보관된 버전이 있을 때 기존 다운로드 경로를 재사용한다. 없을 때 가짜 파일이나 다른 회차 파일을 제공하지 않는다. 이 범위에서 새로운 PPT 편집·생성 UI를 추가하지 않는다.
- 현재 회차와 선택한 과거 이력을 구분하고 현재 작업으로 돌아갈 수 있게 한다. 회차·파일·코멘트의 버전이 바뀐 오래된 확인창은 충돌로 처리한다.

## D10. 파일 업로드 UI 개선

- **Chosen — 사용자 승인 범위와 비교 보고서에서 도출한 구현 기본값**: R3~R5를 공통 컴포넌트로 보완한다.
- **Rationale**: 실제 등록 기능은 이미 구현되어 있으므로 데이터 모델을 다시 만들기보다 기획과 다른 진입·정보 표시를 바로잡는다.
- 분류별 `+ 파일`은 즉시 OS 파일 탐색기를 연다. 선택한 파일이 있으면 설정 모달을 열고, 탐색기 취소만으로 빈 설정창이나 저장되지 않은 변경 경고를 띄우지 않는다.
- 다중 선택, 분류 영역/모달 드롭, 모달의 추가 파일 선택, 개별·일괄 설정, 검증 실패 표시를 유지한다. 선택 경로에 따라 50MB·30개 검증이 달라지지 않는다.
- 웹 카드에 참고 기간을 표시하고, 종류·등록 정보와 함께 공통 메타데이터 표시를 사용한다.
- 우선순위 배지에 필수·우선·일반·제외의 의미를 구분하는 스타일을 제공한다. 색상 외 텍스트도 유지하며 공통 Dadam 토큰/컴포넌트로 관리한다.
- 저장 안내나 업로드 모달의 짧은 문구로 `이 브라우저에 저장` 범위를 알린다. 불필요한 예시 데이터·화면 안내 배너를 복원하지 않는다.
- 기존 3개 영역·회차별 목록·자료 정보·설정·삭제를 유지한다. 카드 밀도 조정은 공통 여백 규칙 안에서 처리하며 별도 목록 형태 개편을 필수 요구로 확대하지 않는다.
- 화면과 업무 검증이 같은 용량·개수 상수를 사용하도록 정리한다.

## D11. 저장·오류·권한 경계

- **Chosen — 기존 저장 규칙 및 코드 기반 기본값**: UI → TanStack Query 훅 → 서비스/도메인 → IndexedDB 경계를 유지한다.
- **Rationale**: UI와 저장소를 분리해 추후 서버 연동 시 업무 규칙을 재사용하고, 현재의 원본·회차 데이터를 보존한다.
- 저장된 프로젝트·회차·파일 Blob·권한·코멘트·완성본을 보존하는 호환 읽기/추가 업그레이드를 설계한다. DB 삭제/재생성이나 새 seed 덮어쓰기로 해결하지 않는다.
- 현재 프로젝트·회차·권한·revision을 저장 시 재확인한다. 멀티탭 갱신, 권한 변경, 저장 용량 부족, 원본 누락, 손상 데이터는 성공이나 빈 상태로 숨기지 않는다.
- 새 프로젝트/회차/메뉴 선택과 모달 종료는 기존 미저장 입력 보호를 공유한다. 파일 대기 목록, 코멘트 입력, 권한 초안을 조용히 버리지 않는다. 완성·재작업도 같은 보호 경계를 사용한다.
- 내부 타입은 Container에서 부분 타입을 유도하고 Zod로 외부 저장값·명령을 검증한다. 새 내부 any/unknown을 도입하지 않는다. 설치된 라이브러리를 재사용한다.
- 로컬 권한 검사는 서버 보안 검증의 대체물이 아니다. 이번 작업에서 Cosmos DB·서버 API·Azure 리소스 또는 실제 메시지 발송을 새로 연결하지 않는다.

## D12. 검증 및 다음 단계

- **Chosen — 기존 사용자 검증 정책 유지**: 브라우저·CUA·E2E·스크린샷/육안 비교·검증용 dev server를 사용하지 않는다. `tests/`를 생성·복원하지 않는다.
- **Rationale**: 2026-10-30 검증 정책 및 2026-11-02 추가 지시가 계속 적용된다.
- 구현 단계에서 타입 검사·lint·build·정적 기획 대응 검토를 수행한다. 필요하면 기존 도구를 사용한 인메모리 저장소 검증을 파일 생성 없이 실행한다.
- 주요 검증: 6개 메뉴의 같은 프로젝트/회차, 사이드바 리뷰 접근, 권한 저장/초안/충돌, 코멘트 프로젝트·회차 격리, 기존 원본 보존, 완성·재작업과 파일/의견 동시 보존, 잘못된 ID·권한 우회 거부, 직접 파일 선택/드롭의 동일 한도, 웹 기간·배지 표시.
- 실제 브라우저 PDF·핀 드래그·반응형 배치·포커스 동작을 실행 검증한 것으로 기록하지 않는다.
- 이번 인터뷰에서는 코드와 결정을 읽고 이 문서만 작성했다. 구현·타입 검사·lint·build·커밋·push는 수행하지 않는다.
- 다음은 `/memory-plan`. 단계는 공통 데이터·선택 경계 → 코멘트/회차 호환 모델 → 상단바·권한·이력 연결 → 파일 UX → 통합 검증으로 계획한다. 작업 파일·스키마·커밋 단위는 계획 단계에서 확정한다. 현재 완료 상태인 `.memory/current.md`는 인터뷰에서 변경하지 않는다.

## 코드 조사로 확인한 사항과 범위 밖 후속

- **기존 기능 재사용**: 회차 전환, 권한 저장, 파일 영속 저장, 과거 의견 읽기, PPT 버전 다운로드, 미저장 입력 보호가 이미 있다. 동일 기능의 헤더 전용 구현을 새로 만들지 않는다.
- **호환성 주의**: 기존 프로젝트 코멘트는 `sectionId`·`slideId`를 필수로 요구한다. 화면 전체 핀을 위한 대상 구분을 계획해야 하며, 빈 문자열이나 임의 슬라이드 ID로 우회하지 않는다.
- **상단바 상태 주의**: 헤더 mock은 2개 프로젝트·고정 역할/회차를 갖지만 작업 카탈로그는 다른 범위의 프로젝트를 제공한다. 표시 정보를 보강하되 선택·권한·회차를 mock 헤더에서 역으로 덮어쓰지 않는다.
- **후속 — 이번에 자동 포함하지 않음**: RFP 등록 결과·원본의 자료함 자동 연계, 관리자 카탈로그 영속화, 실제 서버/공유 저장·권한, AI 분석/리뷰 본문, 알림 발송, 프로젝트 기본정보 수정·활동 로그, 새 제작 편집기 복원.
