- 상단 `KPC | 제안서 AI` 제목, 접기·펼치기 버튼
- 메뉴 순서·간격·구분선·빨간 활성 표시

- 좁은 화면에서 기존 모바일 메뉴 열기·닫기 동작 및 메뉴 영역 세로 스크롤
- 각 메뉴에 대응하는 실제 URL과 간단한 안내 화면, 헤더의 현재 화면명 연동

제외:

- 프로필 클릭 팝오버·모달 및 그 내부 전체 기능
- 권한 전환 버튼, 알림, 토큰 사용량, 토큰 신청, 계정 상세, 환경 설정
- 프로젝트 선택기·프로젝트 상태·진행 결정·잠금·업무 건수와 배지 집계
- RFP 업로드 폼, 목록 데이터, AI 처리, 제작 도구, 관리자 업무 기능
- 전체 목업 이식, 원본 JavaScript 실행·삽입, 가짜 세션·관리자 로그인

프로필은 이번 단계에서 비대화형 표시 영역이다. 클릭 가능한 메뉴인 것처럼 `aria-haspopup`나 모달 이벤트를 붙이지 않는다. 실제 로그인한 경우 기존 로그아웃 링크는 작게 유지하여 인증 기능을 끊지 않는다.

## D04. Fluent UI와 파일 관리

사용자 추가 지시에 따라 Fluent UI React v9를 사용한다. `FluentProvider`, `Button`, `Avatar`, `Badge`, `Divider`, `Tooltip`과 Fluent 아이콘을 활용하고 메뉴 이동 자체는 Next.js `Link`로 처리한다. 별도 메뉴 UI 라이브러리는 도입하지 않는다.

이번에 만드는 사이드바와 수정하는 셸·헤더는 같은 TSX 안에 `const useStyles = makeStyles({ ... })`를 정의하고 컴포넌트에서 `const styles = useStyles()`로 사용한다. 조건부 스타일 결합은 `mergeClasses`를 쓴다. `.module.css`와 CSS 문자열 `<style>`을 새 UI에 사용하지 않는다. 로그인·홈 등 이번 작업과 관계없는 파일 전체의 스타일 변환은 포함하지 않는다.

Fluent UI 기본 파란색으로 원본의 빨간 선택 상태를 덮지 않도록 작업 영역 테마와 사이드바 스타일을 지정한다. 기존 전역 CSS 초기화는 유지한다. Fluent 공급자는 인증된 앱 레이아웃에만 추가하여 로그인 화면까지 재디자인하지 않는다.

## D05. URL과 간단한 화면

메뉴 메타데이터는 `config/sidebar.ts` 한 곳에서 관리한다. `/workspace/[screen]` 서버 페이지 하나가 허용된 15개 screen을 받아 각각 `<메뉴명> 화면입니다.`를 출력한다. 예: `/workspace/register` → `RFP 등록 화면입니다.`. 알 수 없는 screen은 404이며 파일명·컴포넌트를 입력값으로 동적 import하지 않는다.

화면이 모두 같은 안내 형식이므로 메뉴마다 TSX 파일 15개를 만들지 않는다. 메뉴마다 서로 다른 URL을 사용하므로 새로고침·직접 진입·뒤로/앞으로 이동이 가능하다. 중앙 내용만 바뀌고 셸과 접힘 상태는 유지한다. 기존 `/` 홈과 `/admin` 관리자 예시 라우트는 유지하며 별도 홈 메뉴를 원본 사이드바에 추가하지 않는다.

## D06. 인증 비활성 미리보기와 활성 권한 검사

사용자가 다음 방식을 선택했다: **메뉴와 빈 화면까지 미리보기 허용, 인증 활성화 시 Admin 권한 검사**.

- `AUTH_ENABLED=false`: 일반 7개와 관리자 8개, 총 15개 메뉴 및 안내 화면을 표시한다. 이 예외는 신규 안내 화면에 한정한다. Azure·DB·Redis·관리자 API를 호출하거나 세션·역할을 생성하지 않는다.
- `AUTH_ENABLED=true`: 기존 `(authenticated)/layout.tsx`의 `requireAppAccess`로 앱 진입을 보호한다. 일반 User는 일반 7개, Admin은 전체 15개를 본다. 미인증·역할 없는 사용자를 셸로 들이지 않는 기존 정책을 유지한다.
- 관리자용 신규 화면은 서버 페이지에서 `requireRole(APP_ROLES.ADMIN, item.href)`를 실행한다. 메뉴 숨김만으로 인가를 대신하지 않는다. 프런트엔드에서 관리자가 된 것처럼 상태를 만들지 않는다.
- 기존 `requireRole` 함수와 기존 `/admin` 라우트의 인증 비활성 404 정책은 변경하지 않는다.

## D07. 하단 프로필 데이터

실제 세션에서는 이름 → 이메일 순으로 표시명을 선택하고 둘 다 없으면 `사용자`를 표시한다. Admin 역할은 `관리자`, 그 외 정상 앱 사용자는 `일반` 배지로 표시한다. 현재 세션 스키마에 부서 정보가 없으므로 부서 필드·Graph 조회를 추가하지 않고 소속 줄은 `KPC`로 표시한다.

인증 비활성 미리보기에서는 `정소담` / `미리보기` / `AI사업본부`를 표시해 원본의 배치를 확인한다. 이는 표시용 샘플이며 인증 상태나 권한 데이터로 사용하지 않는다. 장식 점은 실제 알림 건수·미확인 상태를 뜻하지 않는다.

## D08. 검증과 보존 범위

메뉴 카탈로그·노출 권한·서버 관리자 가드·허용 URL을 단위 테스트로 검증한다. 실제 화면은 펼침/접힘, 메뉴 15개 이동, 뒤로/앞으로, 모바일, 작은 높이, 키보드 포커스, 프로필 클릭 무반응을 확인한다. Fluent/Griffel SSR 스타일이 최초 HTML에 포함되고 클라이언트 이동 이후에도 유지되는지 확인한다.

로그인·팝업 인증·로그아웃·Azure 공통 서비스·인증 캐시·CSP·기존 관리자 예시의 의미를 보존한다. Next.js·React 업그레이드나 기존 audit 취약점 수정은 이 계획에 포함하지 않는다.
