## Context

## D01. 구현 범위

HTML의 사용량 KPI·그래프·분석·최근 내역과 토큰 신청 폼을 구현한다. 사용량→신청 및 신청→사용량 전환, 입력 검증, 로컬 승인 대기 목록·안내까지 포함한다. 실제 API/DB·승인/거절·한도 지급·관리 화면·Azure 연결은 후속 범위다. 사용자의 로그인 후순위 결정과 현재 서버 인증·인가 경계는 유지한다.

## D02. 공용 UI

설치된 Fluent UI v9의 단일 Dialog를 `components/ui/ModalFrame.tsx`로 감싼다. 사용량 760px, 신청 560px이며 좁은 화면에 맞게 줄인다. 기존 SegmentedControl에 chips 변형을 추가해 요청량 선택을 공용화하고 기존 설정용 기본 디자인을 보존한다. 차트는 HTML/CSS로 구성한다. TSX 내부 makeStyles를 사용하며 새 패키지나 CSS Modules는 추가하지 않는다.

## D03. 데이터 일관성 — 사용자 확인 완료

질문: HTML 일별 사용량은 62.2K, 상단과 프로젝트별 사용량은 72.4K인데 어느 기준으로 맞출지.

사용자 답변: **구성은 HTML대로 유지하고, 일별 값의 비율을 유지하며 합계를 72.4K로 맞추기.**

원본 K 배열 `[2.1,3.4,1.2,0,0,4.8,5.6,3.9,4.2,2.7,0,0,6.1,7.4,5.2,4.9,3.8,0,0,6.9]`에 724/622를 적용하고 100토큰 단위 최대 나머지 배분(동률은 앞 날짜 우선)으로 확정한다.

확정 토큰 배열: `[2500,4000,1400,0,0,5600,6500,4500,4900,3100,0,0,7100,8600,6100,5700,4400,0,0,8000]`.

집계 기간은 2026.10.01~10.20, 경과20일/31일로 고정한다. 월말 예상은112220이다. 현재 날짜에 따라 예시 수치를 바꾸지 않는다.

## D04. 신청 규칙

초기 선택 +50K. 직접 입력은 안전한 양의 정수 K, 사유 trim 후 2자 이상, 프로젝트는 3개 예시와 프로젝트 외 사용 중 선택한다. 신청을 다시 열면 요청량·사유는 초기화하되 프로젝트 선택은 유지한다. 사유 예시는 현재 사유를 교체한다.

신청은 생성 시각·신청자·프로젝트·금액·사유와 pending 상태로 메모리에 보존한다. 최신 대기 내역을 프로필과 신청 화면에 표시한다. 이전 신청이 있어도 새 신청을 허용한다. **신청 성공으로 100K 실제 한도를 증가시키지 않는다.** 예상 한도만 이번 신청량을 더한다. 성공 Toast는 로컬 미리보기 접수임을 알린다. 전체 새로고침하면 초기화한다.

## D05. 모달 수명과 포커스

레이아웃 Provider 안에서 AppShell과 형제인 컨트롤러를 한 번만 마운트한다. 프로필 팝오버를 닫은 다음 모달을 열고 두 화면 전환 시 새 제목에 포커스를 준다. 모달이 열려 있으면 모바일 사이드바가 Tab/Escape를 처리하지 않는다. 모달 닫기는 프로필 버튼으로 복귀하고, 경로 변경에 따른 닫기는 새 화면의 포커스를 유지한다. 기존 사이드바의 body 잠금과 Dialog의 잠금을 중복 수동 관리하지 않는다.

## D06. 기존 수정 보존

탭 중앙 정렬·선택 빨간색·관리자 빨간 아바타/배지·팝업의 검정 아바타/흰 글자·스크롤바 숨김·삭제한 안내 문구·구분선 여백을 보존한다. 계획 시작 시 미커밋 UI 파일 3개는 이번 계획 작성으로 수정하거나 커밋하지 않는다.
