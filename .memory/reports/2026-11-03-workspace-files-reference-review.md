## 판정

**파일 자료함 자체의 핵심 기능은 구현되어 있고, 이번에 실행한 저장·변경 검증도 통과했다. 다만 기획 HTML과 화면·업무 흐름 전체가 동일하게 완성된 상태는 아니다.**

가장 큰 차이는 프로젝트 공통 상단바와 제작 화면 연결이다. 파일 업로드·목차·제작 설정은 통합 작업 상태를 사용하지만, 현재 제작 화면은 사용자의 요청으로 동료 화면을 복원한 상태이며 별도 mock 프로젝트 상태를 사용한다. 따라서 파일 화면의 프로젝트 선택·회차 전환이 제작 상단바와 일치한다고 보장할 수 없다.

실제 서버 업로드·AI 분석·웹 검색·다른 사용자와의 파일 공유는 이전에 후속으로 합의했다. 이를 누락 버그나 이미 완성된 기능으로 계산하지 않는다. 기획 HTML의 고정 시연 본문·비표시 KMS 및 검색 분기도 필수 구현 누락으로 계산하지 않는다.

## 보완 사항과 우선순위

### R1. 파일 화면과 현재 제작 화면의 프로젝트·회차 연결 — 높음, 메뉴 간 연결 문제

- 기획은 `pageProject()`와 `FILES`의 현재 프로젝트를 공통으로 사용한다(HTML 1881, 2508~2521). 제작 자료 탭도 같은 자료를 사용한다(3441~3446).
- 파일 화면은 [FilesWorkspace.tsx](../../components/workspace/files/FilesWorkspace.tsx#L25)의 `useWorkspaceSelection`과 통합 작업 저장소를 사용한다.
- 현재 라우트는 [page.tsx](../../app/(authenticated)/workspace/[screen]/page.tsx#L40)에서 files와 write를 각각 `FilesScreen`, `CommentsWorkspace`에 연결한다.
- 제작의 [ProjectHeaderProvider.tsx](../../components/common/ProjectHeaderProvider.tsx#L28)는 `useState("mois")`와 별도 mock 목록을 사용한다. 파일 화면의 선택값/회차를 구독하지 않는다. 제작 상단바의 완성·재작업 확인 버튼도 비활성 상태다(`ProjectHeader.tsx` 197, 210).
- 예: 파일 화면에서 교육 프로젝트로 바꾸거나 다음 회차를 시작해도, 제작 상단바는 자신의 기존 프로젝트·회차를 표시할 수 있다. 현재 제작에는 파일 자료함을 소비하는 자료 패널도 연결되어 있지 않다.
- **구분:** 최근 사용자가 요청한 동료 제작 화면 복원에 따른 현재 연결 상태다. 이 보고서에서 복원을 취소하거나 다른 제작 화면으로 교체하지 않는다. 추후 동료 화면을 유지하면서 공통 선택·회차·자료 연결을 보완할 사안이다.

### R2. 기획의 프로젝트 공통 상단바 일부 미대응 — 중간, 범위 차이

- [FilesWorkspace.tsx](../../components/workspace/files/FilesWorkspace.tsx#L111)에는 프로젝트 선택·자료 한도·다음 회차만 있다.
- HTML의 발주처·마감·내 역할, 공통 상태/이력, 설정 진입은 이 메뉴에 없다. 회차 번호 자체는 본문에 있으므로 회차 표시가 전혀 없는 것은 아니다.
- 최초 파일 작업의 D03/D12는 간결한 프로젝트 선택 도구를 합의했다. 따라서 당시 범위 누락이라고 단정하지 않되, 현재 요청처럼 HTML 전체 구성을 비교하면 부분 대응이다.
- 권장: 기존 공통 디자인과 동료 상단바를 검토해 공통 프로젝트 도구를 정리하되, 현재 동료 상단바를 단순히 추가해 서로 다른 상태가 두 번 보이게 만들지 않는다. R1과 함께 해결한다.

### R3. 로컬 저장 범위가 정상 흐름에 드러나지 않음 — 중간, 상태 안내

- 실제 파일은 브라우저 IndexedDB에 저장하지만 정상 추가·저장 UI에는 이 저장 범위가 표시되지 않는다. 성공 안내도 [FilesWorkspace.tsx](../../components/workspace/files/FilesWorkspace.tsx#L86)의 일반적인 “변경 사항을 저장했습니다.”다.
- 서버·다른 기기·동료에게 공유된 것으로 오해할 여지가 있다. 기존 D01/D02/D12의 로컬 저장 경계를 화면에서 확인하기 어렵다.
- 권장: 불필요한 화면 안내 배너를 추가하기보다 파일 추가 모달이나 저장 완료 메시지에 “이 브라우저에 저장했습니다”처럼 짧게 범위를 표시한다. 기존 사용자 요청으로 제거한 “예시 데이터/화면 안내”를 복원할 필요는 없다.

### R4. 파일 추가에 클릭이 한 단계 더 필요함 — 낮음, 기획과 다른 UX

- HTML은 분류별 추가 버튼에서 즉시 파일 탐색기를 연다(3827~3831).
- 현재는 [FileCategoryPanel.tsx](../../components/workspace/files/FileCategoryPanel.tsx#L30) → 빈 모달 → [FileUploadDialog.tsx](../../components/workspace/files/FileUploadDialog.tsx#L31)의 파일 선택이다.
- 권장: 분류의 `+ 파일`은 탐색기를 바로 열고 선택 결과로 설정 모달을 띄운다. 모달에서 파일을 더 추가하는 기능과 드롭은 유지한다.

### R5. 목록에서 확인 가능한 정보와 우선순위 시각 구분 감소 — 낮음, 정보 표현

- HTML `refMeta()`는 웹 링크와 참고 기간을 함께 표시한다(3833~3834). 현재 [FileResourceCard.tsx](../../components/workspace/files/FileResourceCard.tsx#L21)는 호스트만 표시하며 기간은 상세 모달에 들어가야 확인된다.
- HTML `PRI_CLS`는 필수/우선/일반/제외를 구분한다(3695). 현재 카드의 우선순위 배지는 같은 색상이며 제외만 카드 불투명도를 낮춘다(15, 26). 텍스트 구분은 유지되어 기능 누락은 아니다.
- HTML은 조밀한 행 목록이고 현재는 개별 패딩·여러 줄·설정/삭제 버튼을 가진 카드다. 목록이 길 때의 실제 화면 밀도는 육안 검증하지 않았다.
- 권장: 공통 `ReferencePriorityBadge` 및 자료 메타데이터 표시 컴포넌트로 기간·우선순위 구분을 보완하고, 많은 자료에서도 간결한 행 형태가 가능한지 검토한다. 색상 외 텍스트 구분은 유지한다.

## 의도적으로 다르거나 후속으로 합의한 부분

- 실제 서버 DB/파일 저장소, 문서 색인·AI 활용, 웹 검색/본문 수집, 사용자 간 공유는 후속이다. 현재는 실제 파일의 로컬 보관과 설정 관리까지다.
- PDF/TXT 이외 Office·HWP 본문 렌더링은 이번 범위에 없고, 파일 정보와 원본 다운로드를 제공한다. HTML의 시연 본문을 실제 문서처럼 표시하지 않는 것이 맞다.
- `KMS`, 검색어·포함/제외 사이트·검색 결과 선택은 코드에 흔적이 있으나 HTML의 현재 표시 폼에는 없다. D04에서 제외했다.
- 샘플 추가, 예시 데이터, 화면 안내는 사용자 요청과 D12에 따라 생략했다.
- 30개는 현재 회차의 파일+웹 합산이며 계승 자료와 참조 제외도 포함한다. 과거 버전까지 모두 누적 계산하지 않는다. 300쪽은 권장 안내이고 페이지 분석·제한 기능이 아니다. HTML의 미일관 적용 상수 `projMB:300` 등을 새로운 제한으로 추가하지 않았다.
- 과거 회차 불변 보관·PM/소유자 권한·동시 수정 충돌 방지는 HTML 시연보다 강화한 요구사항이다.
- 프로젝트 카탈로그는 `config/workspace-projects.ts`의 `createAdminSeed().rfps` 기반 mock이다. RFP 등록 메뉴의 새 데이터 및 첨부 원본이 자동으로 파일 자료함에 전달되는 전체 업무 연결은 현재 없다. 기존 mock 프로젝트 합의에 따른 통합 후속 항목이며 파일 추가 자체의 실패와 구분한다.

## 컴포넌트화 상태

현재 구조는 화면 전체에 UI와 저장소가 뒤섞인 형태가 아니다.

`FilesScreen → FilesWorkspace → FileRoundSection → FileCategoryPanel → FileResourceCard`

입력은 `FileUploadDialog` / `FileSettingsDialog` / `WebReferenceDialog`, 공통 설정은 `FileReferenceFields`, 미리보기는 `FilePreviewDialog`와 `useFilePreview`로 나뉜다. `WorkspacePage`, `WorkspaceCard`, `ModalFrame`, `DadamControls`, `SegmentedControl` 및 공통 여백 토큰을 재사용한다.

데이터는 TanStack Query 훅 → `WorkspaceFileService` → `IndexedDbFileRepository`로 분리되어 있다. 화면의 카테고리·카드 표현을 바꾸더라도 파일 저장 규칙을 함께 다시 작성할 필요는 없다. 다만 이 경계가 있다는 것만으로 서버 연결이 완료되는 것은 아니다.

## 이번에 실제 실행한 검증

| 검증 | 결과 |
| --- | --- |
| 기획 HTML 표시 마크업·이벤트·관련 스크립트 정적 비교 | 위 대응표 및 R1~R5 확인 |
| `npm run typecheck` | 통과 |
| `npm run lint` | 통과 |
| Node + 기존 tsx/fake-indexeddb 인라인 검증 | 21개 조건 통과 |

인라인 검증: 초기 빈 자료함, 동명 파일 별도 ID, 실제 원본 바이트 복원, TXT 내용 미리보기, 잘못된 확장자 및 일괄 저장 롤백, 빈 파일, 50MB 초과, 웹 링크 정규화·기간 보관, 비HTTP 링크 거부, 저장소 재연결 후 자료·선택 복원, 회차 계승/과거 읽기 전용, 과거 지침 불변/현재 지침 수정, 원본 Blob 재사용, 삭제/복원, 회차별 분류 순서 보존, 파일·웹 합산 30개 제한, 오래된 편집 충돌, 타인 자료 삭제 거부, 프로젝트별 자료 분리를 확인했다.

실제 사용자 IndexedDB를 열거나 변경하지 않고 별도 인메모리 IDBFactory만 사용했다. 테스트 파일·`tests/`를 생성하지 않았다. 이번에는 빌드를 재실행하지 않았다.

기존 검증 정책에 따라 브라우저·CUA·E2E·스크린샷·dev server 검증은 하지 않았다. 실제 반응형 배치·드래그·포커스·PDF 뷰어·브라우저 저장 한도 및 서버/인증 운영 검증을 통과했다고 주장하지 않는다.

## 권장 작업 순서

1. R1/R2: 동료 제작 화면을 유지하면서 프로젝트·회차 상태와 공통 상단 도구의 연결을 먼저 정리한다.
2. R3/R4/R5: 저장 범위 표시, 파일 추가 단계, 웹 기간·우선순위 표시를 공통 컴포넌트로 개선한다.
3. 서버 준비 단계에서 프로젝트/RFP 원본 연계·공유 저장·서버 권한·검색/AI를 별도 구현한다.
